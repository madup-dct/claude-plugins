# Voice Guide

## Shared Principles

- Facts are fixed unless the user explicitly asks to verify or change them.
- Names, dates, numbers, units, quotes, acronyms, and requested actions stay exactly as provided; copy supplied date/number/unit/name tokens verbatim. No abbreviation or reformat: `8월 4일` must not become `8/4`.
- Lead with the point. A reader should know the fact, decision, or ask in the first line.
- Use concrete subjects and verbs. Prefer "민지가 수정안을 공유합니다" over abstract constructions.
- Preserve register and mode. Do not flatten formal writing into casual chat or inflate short chat into report language.
- Short text does not need headings or bullets unless they make scanning easier right away.
- One clean pass is enough. Remove empty transitions, translation-like phrases, inflated claims, decorative metaphors, and mechanical parallelism without rebuilding the whole piece.
- In rewrite tasks, ready-to-use copy comes first. No commentary, no labels, no explanation unless requested.

## Mode 1: Slack / Email

- Start with the current status, decision, or ask.
- Preserve the supplied calendar exactly. Do not "correct" a date just because it looks unusual.
- Keep the path clear: context -> impact -> action or owner.
- A short message can stay as one paragraph. Force bullets only when there are multiple actions or owners.
- Favor direct wording such as "일정이 이틀 밀렸습니다" over preambles like "먼저, 결론부터 말씀드리겠습니다."

## Mode 2: Report

- Keep what already works. If the baseline is factual and concise, make the smallest useful edit.
- In a longer brief, use a one-line conclusion before detail when it improves scanning.
- If the source contains an operational chain, keep `risk -> action -> status -> decision gate` in that order. Do not invent a missing action, status, or gate.
- Keep the order factual: fact -> interpretation -> implication, then next action only when supplied or requested.
- Do not invent follow-up timing, owner, or reporting promise.
- Replace abstract nouns with observable language.
- Avoid unsupported value statements, vague momentum language, and unnecessary scene-setting.
- When metrics are provided, let them carry the weight instead of adding hype around them.

## Mode 3: Proposal

- Write for an advertiser or decision-maker, not for an internal workshop.
- Put evidence before claim. Show the friction, data, audience behavior, or market context first, then state the recommendation.
- Put the strongest evidence first. Label supporting references and hypotheses instead of presenting every source at the same confidence.
- Use controlled contrast only when the source supports both sides and the contrast points to one decision.
- Make one promise at a time and support it.
- Do not convert proof into an unsupplied budget move, rollout promise, or guarantee.
- Avoid airy benefit language such as "시너지를 극대화" or "혁신적인 솔루션."
- Proof can be a metric, a user behavior, a channel constraint, or a concrete observation. Without proof, lower the claim.

## Mode 4: Presentation Copy

- Every line must pass the read-aloud test. If it sounds stiff aloud, rewrite it.
- Headlines should sound speakable, not literary or ceremonial.
- Avoid decorative contrasts, slogan-like declarations, and abstract noun piles.
- A controlled contrast is acceptable when evidence-backed and easy to say aloud.
- A short support line is fine when the headline alone is too thin, but keep the pair easy to say in one breath.
- Separate advertiser, internal, Q&A, or talk-track views only when requested or already present in the source.
- Reserve dramatic phrasing for cases where the user explicitly wants it.
